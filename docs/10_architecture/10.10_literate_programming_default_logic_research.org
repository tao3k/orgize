Question: what should Orgize provide for AI Agents and humans working
across independently organized code, comments, documents, SysML v2 models,
and engineering evidence?

Working position, revised after the user discussion on 2026-10-28:
Orgize is the Org document participant in that workflow. Code retains its
native module/file/symbol organization; documents retain their explanatory
organization. References connect them. Existing Deterministic Engineering,
SysML v2, GQL, OrgContract, and ASCENT mechanisms should be composed at
their owning boundaries rather than reproduced as an Org-only system.

The earlier recommendation to prioritize Org-to-Catala compilation and
place rule implementations and relationship declarations in Org is
withdrawn as the general direction. Embedded code and tangling remain
available for cases that choose them; they are not prerequisites for
Agent use or the architectural center of this research. The paper and
Catala remain comparison evidence, not a mandate to adopt their source
layout or default logic.

** Details that need explicit treatment before implementation

In the author's notation a lower rule under =<= dominates a higher one
(p. 65). An implementation must document its direction; a numeric
priority field with unspecified ordering is insufficient. The paper's
worked procedure accepts consistent rule implications in priority order,
not merely a sequence of tests whose antecedents are currently true
(pp. 65-66 and 71-72). These are different candidate semantics.

The p. 76 displayed equivalence contains =not Deductible= where the
preceding sentence says the interest is not personal. This is visible in
the downloaded PDF, not just extracted text. Treat it as an apparent
formula/prose inconsistency in this copy. Do not silently correct the
quotation or use it as an executable specification. A separate model
derived from that sentence would use =not Personal= and must be labeled
our reconstruction, with its assumptions and truth table.

Our finite Boolean diagnostic fixes =Interest=true=. The printed form
then has no solution when =QRI=false=, and the sole solution
=Deductible=true= when =QRI=true=. The reconstructed prose formula has
one solution for each supplied pair of =Personal= and =QRI=:

| Personal | QRI | Reconstructed Deductible | Strict QRI implies Personal |
|----------+-----+--------------------------+-----------------------------|
| false | false | true | consistent |
| false | true | true | inconsistent input |
| true | false | false | consistent |
| true | true | true | consistent |

The [[file:../../.cache/research/lawsky-2017/formula-diagnostic.json][local diagnostic receipt]] records this check. This is a four-row
closed Boolean exercise, not a proof about incomplete facts, tax law,
the entire paper, or Catala. Unknown is not a value in this calculation.
No author erratum was located or assumed.

Another semantic hazard is material implication versus a forward rule.
With a strict fact =not B= and an accepted implication =A implies B=,
classical closure can derive =not A=. A forward matcher whose only action
is firing on =A= would not derive that result. This original minimal
example motivates checking semantics before replacing the paper's
consistency procedure with an exception matcher.

** Our assessment

The paper is useful as a source of modeling questions. It does not
establish that arbitrary rules admit a unique preferred result, that
sorting by specificity always determines priority, or that legal prose
can be translated automatically without interpretive decisions. A
prototype must choose semantics for incomplete facts, incomparable
exceptions, cycles, conflicting strict premises, and changes of source.

For this research, the useful hypothesis is that independently owned
sources can remain inspectable through accurate references and reusable
constraints. No conclusion here requires moving code, implementation
comments, or system-model relationships into Org. Correct output on one
closed set of facts does not establish faithful representation of the
source, or explain what changes when an exception is added.

* AI Agent first: independent organization, connected access

This section records the user's architectural direction and our revised
research proposal. It is not a claim of completed integration.

Traditional literate programming can make one document the shared reading
and implementation surface. In an AI Agent plus human workflow, that
physical concentration is unnecessary: an Agent can retrieve code, local
comments, models, tests, and design discussions from their native places.
The human can retain a coherent explanatory document without inheriting
the compiler's module ordering or carrying a duplicate copy of the code.

The relevant improvement is greater effective bandwidth across sources,
not unlimited context or automatic correctness. An Agent needs precise
navigation, bounded retrieval, and checkable updates. Orgize should
support those operations on Org documents and compose with the tools that
already serve other sources.

A reference is a sufficient connection when the target and its existing
context answer the question. Do not require an additional Org relationship
annotation for every link. Implementation intent and local invariants can
already live in code comments; system relationships can already live in
SysML v2. Repeating them in Org creates another authority to maintain.
Where a workflow needs explicit ownership facts or constraints, reuse
OrgContract and ASCENT composition instead of inventing a general Org
ontology. Documentation may associate tests and results without embedding
their implementation or replacing the test runner.

* Responsibility boundaries

| Surface or component | Responsibility in this direction | Orgize boundary |

| Tests and execution owners | Test implementations, commands, actual outcomes, and result artifacts. | Allow documents to reference these artifacts; a link or displayed result is not execution. |
| SysML v2 and its tooling | System model elements and relationships already owned by that model. | Reference model elements and consume owner-supplied projections; do not recreate the model as Org headings/properties. |
| Deterministic Engineering | Existing engineering method and ownership/evidence conventions. | Reuse those conventions; this note does not establish another engineering methodology. |
| Org documents | Research, explanation, discussion, decisions, and references suited to document form. | Parse, locate, query, and support source-preserving document edits. No mandatory universal metadata schema. |
| GQL and existing graph infrastructure | Queries over information provided by participating source owners. | Supply Org facts through an adapter; do not add another cross-source graph/query engine to Orgize. |
| OrgContract | Express and check admitted document-side contracts using existing capabilities. | Reuse contract IDs, scope, queries, and diagnostics; qualify any needed extension explicitly. |
| ASCENT | Rule evaluation over supplied facts for the composed workflow. | Supply facts/results through the owning integration; do not turn the Org parser into an inference engine. |

* OrgContract plus ASCENT: establish ownership and check constraints

Use the combination the user identified to let the model establish the
needed ownership information and constraints. That information may be
read from code comments, model elements, engineering conventions, tests,
or documents. Establishing a usable projection does not require moving
its authoritative source or hand-authoring every relationship in Org.

A proposed workflow, assembled from existing responsibilities:

1. Retrieve the relevant Org fragments and the independently owned code,
   comments, SysML elements, tests, and engineering conventions. Preserve
   the source identity supplied by each owner.
2. The Agent establishes candidate ownership assignments and associations
   from that material, reusing existing declarations first. Keep a source
   reference for an extracted fact; distinguish a model suggestion from
   an explicit owner declaration. Ask for review only where the workflow
   requires a decision that existing sources do not settle.
3. Check document-local shape and requirements with OrgContract. Supply
   admitted facts from the participating owners to the ASCENT integration
   for the rule checks and derived ownership information it defines.
   GQL can retrieve or present the connected information using its existing
   infrastructure. None of these steps requires all facts to be Org nodes.
4. Return conflicts, omissions, and candidate changes with references to
   the responsible sources. A rule's diagnostic is a checked consequence
   of its supplied facts and rules, not a certification that model-extracted
   facts accurately describe an implementation.
5. Apply an authorized correction where the content belongs: code/comment,
   SysML model, test, engineering record, or Org prose. Refresh projections
   and rerun affected checks. The host owns storage and publication;
   ASCENT owns rule/logic evaluation, not the Agent interaction loop.

Example constraints to investigate in that composition, only where the
existing project policy requires them:

- An ownership assignment resolves to an existing target in the relevant
  source revision and allowed scope.
- Mutually exclusive ownership assignments cannot both be accepted for
  the same object under the selected policy. Do not assume every object
  must have exactly one owner; shared ownership may be explicitly valid.
- A document cannot silently override a source owner's declaration or a
  SysML relationship through an inferred association.
- A verification claim references the appropriate test/result and source
  revision; a linked test definition alone does not mean it ran or passed.
- A changed or missing source prevents an old derived assignment from
  being presented as a freshly checked current result.

These are proposed constraint cases, not new built-in contract forms or
ASCENT predicates. Prefer existing policy and fact vocabulary; this note
intentionally introduces neither an Org relationship taxonomy nor a
second universal schema. Rule results can make inconsistencies visible;
passing constraints does not prove arbitrary prose/code equivalence.

* What Orgize actually needs to do

The following is a prioritized research backlog. Existing capabilities
are inputs; the list is not a declaration that each capability is absent.

| Priority | Orgize contribution | Qualification needed |
|----------+---------------------+----------------------|
| P0 | Accurate, non-mutating Org parsing and source-backed Element projection. | Preserve text, hierarchy, IDs, links, properties, and ranges; keep source identity and graph-local identity distinct. |

they do not determine where a project's implementation must live.

* Revised falsifiable experiments

These are proposed experiments, not completed acceptance results. They
replace the earlier primary Org-to-Catala compilation and embedded-rule
experiments. No new framework or runtime integration is implemented here.

** E1: navigation across independently organized sources

Use an ordinary Org research/design note referencing a code function, its
existing comment, a SysML element, and a test/result artifact in their
native locations. Let the Agent retrieve the relevant material through
existing resolvers and GQL composition. Do not move code or duplicate the
model to construct the fixture.

Accept if each reference reaches the intended target and version, Org
fragments retain their outline context, and broken/ambiguous references
are visible. Reorder headings, rename a code symbol, and change a target
revision. The checks must not silently redirect an old reference to a
same-named object. Resolver behavior belongs to the respective owner;
Orgize is assessed on faithful Org projection and source localization.

** E2: model-established ownership with OrgContract and ASCENT

Use a small real consumer workflow and its existing ownership conventions.
Have the Agent establish candidate assignments from code comments, model
facts, and document references. Apply document-side contracts and the
ASCENT rules selected by the consumer. Keep originals in their own files.

Exercise an accepted assignment, a missing target, an unsupported model
suggestion, a policy-forbidden conflict, and an explicitly allowed shared
assignment. Distinguish failures of document shape, source resolution,
fact admission, and rule evaluation. Check which stage detects each case;
model confidence is not a passing contract result. Report unavailable
adapters as gaps instead of substituting fabricated input facts and
calling the workflow integrated.

** E3: change handling and correction at the actual owner

Change code or a SysML model while leaving Org prose untouched. Identify
which references, derived ownership information, and verification claims
need rechecking. Correct the owning source where necessary, regenerate
its projection, and rerun affected contracts/rules. Separately update
only explanatory prose and check which downstream work is actually needed.

Accept if the workflow preserves unrelated changes, distinguishes old
results from current checks, and produces reviewable source-specific
edits. A stale relationship warning does not prove the explanatory prose
is wrong; an Agent assessment of prose is separate from mechanical
reference and constraint checks.

* Recommendation and remaining work

Prioritize source-backed Org access and the existing OrgContract plus
ASCENT/GQL composition for an AI Agent and human workflow. Let code,
comments, models, tests, and documents keep their natural organization.
Use references where sufficient and existing rule/contract mechanisms
where ownership information or constraints need to be established.

Next, inspect the actual consumer integration and select one small
cross-source task for E1-E3. Determine the missing Org-side capability
from that experiment before adding APIs. The research does not authorize
a code migration, an Org-only relationship system, a replacement SysML
model, or a new default-logic runtime. Catala remains a useful reference
for source-aware diagnostics and explicit language semantics.
