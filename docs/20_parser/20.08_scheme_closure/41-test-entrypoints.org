#+title: Native test and benchmark entrypoint convergence

* Ownership

Cargo owns Rust test discovery, executable selection and failure status.
Criterion owns production sampling, calibration, baselines and reports.
Gerbil's existing test harness owns Scheme suite execution. ASP's existing
Scheme benchmark API remains the Scheme sampling owner. No new shell runner,
test framework, native scheduler or parser implementation is introduced.

The native program manifest has one top-level Just export. A nondefault
manifest can be selected once by the caller. SDK/compiler/library discovery
remains owned by gerbil-scheme-rust; immutable parser REV remains in manifests.
Orgize now calls the existing upstream compiler-discovery API rather than
requiring =GERBIL_GSC=. Explicit overrides remain validated by that API.
Platform-specific Darwin settings and workspace optimization profiles are
unchanged. Repeated build receipt commands remain qualification-only.

* Direct entrypoints

| Purpose | Entry |
|---------+-------|
| Rust source checks | =just check runtime-rust= or =runtime-scheme= |
| Rust semantic/lifecycle tests | =just test runtime-rust= or =runtime-scheme= |
| Criterion production sampling | =just bench runtime-rust [Criterion arguments]= |
| Fixed-count native qualification | =just qualify runtime-rust OUTPUT= |
| Scheme source suites | =just scheme-test PARSER_LIB POO_LIB= |
| Scheme linked C FFI suites | existing =scheme-closure-receipt= |
| Scheme Fold sampling | existing =scheme-event-benchmark= and ASP API |

Exclusive first native startup remains isolated from pure libtest cases'
concurrent host/stdio work. This is an existing FFI contract, not a new blanket
ban on concurrent parsing. The other integration targets remain concurrent.
Scheme C FFI tests still require a linked native executable; an interpreted
source command cannot be substituted for that link qualification.
Cargo discovers all tests and examples, including HTML, LaTeX and Markdown
export targets. The isolated startup case is skipped only in the second
invocation, so it executes once. CI preserves workspace coverage and runs
Criterion smoke checks separately with =--test=, not libtest's =--skip=.
Both semantic invocations expose actual case output with =--nocapture=;
they do not generate synthetic progress messages.
The CI startup invocation also selects the workspace: restricting it to
=-p orgize= rejects the matrix's =orgizepy/runtime-*= feature. The exact test
filter still executes only the designated startup fixture; other libraries'
cases are selected by the complete second invocation.

* Criterion versus qualification

=org_runtime= is now solely a Criterion entrypoint. It neither interprets
ambient corpus environment variables nor dispatches subprocess workers.
It retains warm fixture measurements and adds full 1,000/10,000-document
Tokio batches with 1/8/64 callers. Each synchronous native call is submitted
and asynchronously awaited separately. All completions and document drops
are timed. Input construction, runtime construction and complete lossless
preflight are untimed. Throughput is documents per completed batch.
Criterion can repeat full batches; no exact-N completion receipt is claimed.
Profiled builds are rejected before native startup or any measurements.
Corpus construction and preflight are lazy inside Criterion's selected
callback: filtered-out groups and =--list= do not parse 11,000 documents.

The previous exact-count corpus/domain experiment moves to a Cargo example,
with its support modules under =tests/support=. Six explicit positional
arguments select mode, output, document counts, callers, domains and repeats.
All seven =ORGIZE_RUNTIME_CORPUS_*= mode/configuration variables are removed.
The original complete roundtrip/checksum, artifact/source/adapter identities,
bounded admission, worker shutdown and real-progress controls remain.
The process-domain protocol is retained solely for independent native-domain
qualification; it is not a production Scheme process fallback or Criterion
measurement. Its performance mode is diagnostic-only.

Ten redundant/unused Rust recipes are removed, including manual binary
launch aliases and stale parser/link diagnostic wrappers. Source headline
tests join the existing Scheme suite invocation; the duplicate compilation
and separate headline test/receipt recipe are removed. Specialized archived
qualification/receipt helpers have not all been removed.

The archived complete-cutover ledger records =f5a1ac1= Windows best-of-five
results of 103.2245ms (initial failure), 83.8839ms (diagnostic rerun) and
81.9714ms (failed-job rerun). It records 81.4664ms for =344c326=.

At =f5a1ac1=, =src/org_aot_events.rs= includes =org_rowan_events.rs= generated
at build time. =src/org_aot.rs= executes that Rust event function, then
=parse_generated_events= and =project_syntax_graph=. Scheme authors the
algorithm, but no Scheme runtime or native FFI executes that historical hot
path. The parser pin is =4f6d9d67a069d823cfabc33511783b58017e08b3=.
This source distinction does not justify the current regression or authorize
restoring the removed Rust/Rowan parser.

| Property | Historical execution | Current native execution |
|----------+----------------------+--------------------------|
| File workers | Parse inline on each scoped worker | Submit parsing to native service |
| CPU parser ownership | Independent generated Rust calls | One Rust-owned receiver or one Scheme actor |
| Event representation | Generated Rust events directly | Scheme tape encoding, FFI transfer, host decoding |
| Shared keyword value helper | Shared generated dispatch | Helper and both call sites retained |

The worker-count formula remains available cores times eight, bounded by
one worker per 64 files. However, =src/org_events/transport.rs= uses
one =OWNER= and processes incoming requests sequentially. The Scheme lane
in =bindings/c/orgize-scheme-runtime.ss= likewise uses one actor with one
job loop. Multiple callers therefore do not preserve the historical CPU
parsing parallelism. Green threads alone do not establish CPU parallelism
for a CPU-bound parser. This is a concrete migration property gap, not a
measured attribution of the entire 84-to-600ms difference.

=keyword-value-event-helper= remains in =event-headline.ss= with both
=keyword-value-span= call sites. There is no source evidence that this
particular historical optimization was dropped. The remaining audit must
compare backend lowering and full event semantics, not count source loops.

Next performance qualification must isolate native owner service, event
encoding, transfer/copy, decoding and ledger projection on a matched host
and corpus, without concurrent builds. Engine/backend optimization and
qualified native lifecycle/concurrency belong upstream. Do not introduce
uncontrolled concurrent Gambit calls, kernel changes, parser subprocess
fallbacks or a reduced corpus to recover a misleading passing number.

* Native SMP capability and Tokio boundary

The existing Criterion corpus already uses Tokio's multithread runtime and
=spawn_blocking= per parse, with 1/8/64 callers and 1,000/10,000 documents.
That is concurrent admission, not proof of parallel Scheme CPU execution.
AOT and FFI are complementary: compiled Scheme native code is reached through
the FFI boundary; AOT does not remove Scheme allocation, GC or processor state.

The selected SDK's =##configure-command-string= reports =--enable-smp=.
Its standalone startup reports parallelism level 1. The upstream bridge's
=native/runtime.c= explicitly sets =params.parallelism_level = 1=; its
=source_surface.rs= test enforces that value. This is the bridge's current
execution policy, not an inherent limitation of FFI or Scheme actors.

The upstream =scheme/test-native-smp.ss= capability probe raises the standalone
native level to 2, joins two native actors with independent checksum results,
and restores the original level. Native =gxi= execution returns zero with
=NATIVE-SMP processors=2= and =NATIVE-SMP actor-checksums=OK=. It proves this
SDK admits that setting and those actors; it does not prove simultaneous CPU
execution, a speedup, AOT parser safety or concurrent foreign-root transfer.
Plain header defaults are not sufficient to identify the configured SDK ABI.

The safe bridge currently rejects a second runtime initialization and makes
its runtime neither =Send= nor =Sync=. Native SMP must be exposed through an
upstream processor/lifecycle contract, not an unsafe trait implementation.
Rust scheduling and Scheme scheduling should remain separately qualified
features, sharing the same compiled parser and semantic controls. A worker
pool also needs a scheduler-safe idle wait and request-owned publication,
shutdown and GC-root transfer; simply spawning more actors is insufficient.

A separate, unprofiled complete-ledger rerun without our concurrent builds
hits the existing five-second real-output watchdog and exits 124. Its receipt
is =target/acceptance/rust-a36c4d1/ledger-no-build-load/plan-ledger.log=.
No latency number or passing admission is extracted from this interrupted run.
