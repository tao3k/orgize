#+title: 20.11 Orgize Benchmark Qualification

* Package boundary

=build.ss= owns the production package. It does not load or build any target
from =t/benchmarks=, and the production =gerbil.pkg= does not declare ASP.
Git checkouts may contain benchmark source files; package installation does
not compile or install benchmark modules, tooling dependencies or receipts.
An empty downstream directory loaded the installed Org Fold and parsed a
document using the production prefix. Both benchmark imports failed module
resolution in that process. The same directory resolved both procedures
after explicitly adding the benchmark output and development prefixes.

Development prepares the existing =dev/gerbil.pkg= in a separate
=GERBIL_PATH=, with the prepared production library on =GERBIL_LOADPATH=.
=just scheme-benchmarks-build= delegates to
[[file:../../build-benchmarks.ss][the opt-in defbuild-script]].
The standard Gerbil Make adapter compiles its declared modules into
=target/scheme-benchmarks/lib=. =just scheme-benchmarks-clean= cleans those
targets through the same specification. No production recipe invokes either
entry. Rust continues to use Cargo's existing Criterion targets.
The Orgize library disables Cargo's implicit library benchmark harness.
The standard unit-test invocation still runs the library tests and gives
the native startup fixture its own exclusive process. The benchmark command
runs the explicit Criterion targets without starting a second parallel
copy of the library test suite.

Prepare the development prefix separately. Run each compiled benchmark in
its own process with the production library before the development library.
Both dependency trees contain POO modules, so this order keeps the production
Parser and POO artifacts together while resolving the benchmark API from
the development prefix.

count and the workload. The output records the admission decision and the
raw samples.

* Measurement matrix

| Boundary | Existing workload | Evidence |
|----------+-------------------+----------|
| Lexical prefix | Scheme prefix probe | ASP per-sample latency and exact predicate result |
| Names and helper state | Scheme name-set and helper batches, measured separately | Matching event values, sample timings, separate runtime-counter diagnostics |
| Fold | Scheme event Fold on the committed Org corpus | Source identity, full event semantics and phase samples |
| Rust caller and owner | Criterion =org_runtime=, both runtime features | Completed documents, caller width and throughput; queue and service spans in separate diagnostic runs |
| Projection | Criterion =org_element_query= and =parse= | Separate projection and parse-plus-projection cases with unchanged inputs |
| Filesystem through query | Existing 2,000-file ledger gate, both runtimes | All five wall samples, result identity and the existing 100 ms gate |

An experiment names one cost and one candidate. Keep fixture, runtime feature,
compiler, host parallelism, iteration count and resource budgets matched.
Start with repeated runs of the same binary to establish variation. Compare
independent processes in A/B and B/A order and retain every sample, failure
and binary identity outside version control. Report P50 and P95 where the
sample count supports them; keep the ledger gate's best-of-five decision
separate. Do not add overlapping queue, service or GC intervals as though
they were disjoint costs.

Use diagnostic builds to split source read, request encoding, owner wait,
Fold and tape emission, Rust decoding and projection. Qualify gains on the
unprofiled public workload with exact event and result checks. The fixed VM
owner retains Scheme values; moving Rust projection onto that owner changes
the contention model and requires independent evidence.

Profiling receipts use =fold= for Scheme traversal, =event_tape= for the
wire representation, =owner= for queue admission and owner service, and
=ffi= for calls and copies across the language boundary.

For the ledger query, enable =runtime-profile= and set
=ORGIZE_PROFILE_PLAN_LEDGER= and =ORGIZE_PROFILE_PLAN_LEDGER_STAGES= to 1.
Run the same prepared release target under each owner. The
=fold.batch.requests= and =owner.metadata.requests= counters distinguish
the two physical request families. Their owner CPU fields measure work on
the owner thread. The overall =ffi.requests_completed= counter also
includes other operations.

* First Fold candidate

In the prior property-scan diagnostic, two 2,000-file samples recorded 145.5
and 165.6 ms of owner thread CPU across 64 completed owner calls. Their
separately observed event decode spans were 3.1 and 2.8 ms. These are sums
from the instrumented workload. The owner samples cover both Fold and
metadata calls, so they cannot identify the marginal cost of a property.

The generated property path expands the value-start and value-end scans at

the existing delimiter check and leaves header-argument interpretation with
the same Fold helper. Compare complete events on the retained property corpus
before timing the candidate. Keep the compiled candidate and all measurements
separate from the PR until the result supports promotion.

and wheel job waits for the artifact from its own platform.
