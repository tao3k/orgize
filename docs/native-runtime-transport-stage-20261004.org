#+TITLE: Native owner admission and result-transfer qualification

* Implementation and measurement boundaries

Both lifecycle choices now return four private request-local diagnostic stages:
native.owner_admission, native.owner_service_inclusive, native.result_copy,
and native.completion_handoff. No Scheme value/root crosses a caller boundary.
Rust transports only durations and its copied bytes; Scheme returns native
malloc storage and four timing words through a synchronous private C entry.
The public orgize.h ABI and ordinary parsing operation remain unchanged.

Admission includes bounded queue admission, queue waiting and its small native
bookkeeping, not just time inside a queue. Service is inclusive: input copying,
UTF-8 decoding, fold, tape serialization and output copying. Rust service also
includes releasing the output root on the owner. The result-copy span includes
allocation and byte copying but excludes that root release. Scheme's completion
timestamp is taken under its completion mutex before signaling; Rust's is taken
before sending its response. Handoff therefore includes signaling, wakeup and
return bookkeeping, with these explicitly different boundary details.

These stages overlap the existing transport/fold/tape stages. Do not sum them
as disjoint components or subtract percentiles to infer unmeasured costs.
Execution-thread CPU does not count helper-thread CPU; wall/thread-CPU
divergence alone is not proof of OS starvation, idle waiting or a GC cause.

The Rust probe starts only in an active caller measurement. The native owner
receives that probe explicitly, rather than consulting its inactive TLS.
It sends back timings, recorded only on the receiving request. Normal builds
compile out the clocks and timing fields. Scheme's ordinary entry passes no
profile storage and performs no new clock calls; its private profiled entry
rejects failed/nonmonotonic clocks instead of using a fallback.

The shared native header changed, so prior binaries and prior native-program
identities do not qualify this implementation. Both variants are rebuilt with
the same declared-header fingerprint and Rust toolchain. The benchmark adapter
identity also includes the new runtime_profile/transport.rs owner.

* Immutable-executable timing control

The prior Rust executable, SHA-256
e6240aa9679527895d841db6737fb9b1283fc46d6a3cd73ed64a4ed0eb6ab4f8,
was retested unchanged on the same 10,000-document/64-caller/8-domain workload.
Its own program, adapter, benchmark, corpus and mode identities all matched
the prior receipt. Throughput changed from 247.30 to 1297.53 documents/s;
mean fold wall changed from 24.124 to 5.713 ms, with mean thread CPU 5.302 ms.
This falsifies crediting that large improvement to this turn's code.

An immediately following new Rust control run achieved 1263.57 documents/s,
with admission/handoff means 0.132/0.094 ms rather than the main matrix's
0.65--0.72/0.31--0.34 ms. The native scheduler's observed delay is variable;
neither its precise OS cause nor an intrinsic fixed channel penalty is proven.
Each immutable control passed its own same-identity gate. The old/new
controls intentionally have different programs/adapters and are NOT admitted
by the strict paired-runtime comparator. These add 20,000 counted performance
completions, separate from the 66,000 main-matrix completions.

* Remaining qualification

Normal profiling-disabled build checks passed both runtime choices, covering
tests, benches and examples (Rust 13.43 s, Scheme 6.82 s). These are compile
checks, not additional cfg-off Rust execution receipts.

The installed Python SDK was rebuilt with maturin 1.15.0 from the offline
cache, then qualified on CPython 3.13.11 for both runtime choices: 16/16 tests
passed each (Rust 1.26 s and 1.47 s on restored default; Scheme 1.46 s).
The new private identity getter reads only static backend/program metadata;
it does not initialize Gerbil or widen the public Python API. The maintained
python-native-test-installed gate checks the expected runtime and exact
native program digest, catching stale/wrong-feature extension admission.
GIL progress, mixed C/Python calls, pre-startup rejection and host-child
checks remain intact. The current development environment is restored to
