#+TITLE: High-concurrency native Org runtime qualification

* What is being measured

Document count and concurrency are independent axes. The matched matrix is
1,000/10,000 distinct documents, 64 closed-loop Tokio caller tasks, and 1/4/8
independent native execution domains. One domain is explicitly a queue baseline,
not evidence of multicore native parsing. Each domain is a fresh exec'd worker
using the same public =Org::try_parse=, compiled Scheme program and projection.
The supervisor does not initialize Gerbil. No initialized runtime is forked;
no Gambit kernel changes or parser compatibility path are involved.

This benchmark pool is not a production process-pool API. Each worker accepts
one active parse at a time; additional requests wait in bounded supervisor
queues. Therefore this lane measures high-concurrency multi-domain scaling,
including transport, not native per-domain request-queue contention or actor
parallelism inside one Scheme runtime. The existing single-domain Tokio driver
can separately exercise simultaneous FFI callers, but is not a replacement for
this multi-domain lane. Both runtime feature choices use the same pool layout.

The corpus reuses the three committed benchmark fixtures and adds unique title,
headline and document-ID text. Distinct documents are verified; this does not
make it a representative corpus of 10,000 independently authored large files.
It measures ordinary Org parse/projection, not isolated Contract compilation,
query evaluation, installed Python overhead or a network-service load profile.

* Measurement boundaries and fail-closed gates

Startup and three-fixture warmup are outside each timer. Every document gets
its own submission/response, lossless check and tree/graph checksum. End-to-end
latency starts before Tokio queue admission and ends after receiving the worker
result: queue, IPC, parse/projection, validation, checksum and response included.
Pure parse/projection latency is also recorded separately. Corpus and ordered
artifact checksums must match across execution-domain counts and runtime features.

The receipt records configured caller/domain counts, observed maximum in-flight
requests and overlapping worker requests, unique worker PIDs, per-worker document
counts and successful exit statuses. Overlapping IPC requests are not a CPU
utilization measurement. The closed-loop workload does not qualify an open-loop
arrival rate, overload policy or p99 service SLO. Memory/CPU profiles and repeated
interleaved samples remain additional performance investigations.

No completion for five seconds fails the batch. Startup handshakes and graceful
shutdown have deadlines. On internal failure the supervisor kills and reaps its
exact children; caller/worker errors cannot produce a successful partial receipt.
Output files use create-new and are published only after the full matrix succeeds.
Outer invocation also has a bounded total deadline through the Justfile workflow.

=just runtime-parallel-matrix-check= requires all six full-scale batches,
33,000 completions, 64 observed in-flight requests and 1/4/8 observed worker
requests as configured. =just runtime-parallel-compare= rejects mismatched
program/adapter/benchmark/corpus/artifact/configuration identities, duplicates,
incomplete results and failed worker lifecycle before reporting throughput/latency.
