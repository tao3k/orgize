* Tokio application lane
native-runtime-tokio-corpus-run uses the existing fixed-count org_runtime lane.
Four Tokio async scheduler threads run 1/8 bounded callers. Each document is
separately spawn_blocking-submitted and asynchronously awaited. Parse, native
waiting, validation, checksum, drop and completion backpressure stay on blocking
workers, not async scheduler threads. max_blocking_threads equals the caller
limit. The native consumer remains single-worker in both features.

Receipts distinguish driver=tokio from driver=std and bind the same corpus,
program and benchmark source. Public parse latency excludes validation/checksum;
submission-to-parse latency additionally includes blocking-pool admission.
Wall throughput includes per-document submission/await and validation overhead.
This is production-style integration of the existing synchronous API, not a
new native async ABI or replacement of the Rust native-owner request queue.

A read-only process snapshot during the Scheme scale run confirmed substantial
browser/window-server load plus other Gerbil and development-environment jobs.
Those processes were not changed. This round is valid for completed-count and
artifact equality checks, but its elapsed-time figures are descriptive local
observations, not qualified causal performance comparisons or a runtime winner.

The first Scheme four-batch invocation hit its 600-second outer deadline.
Its three fully completed stdout receipts are retained separately in
native-runtime-tokio-pr7c-scheme-completed-before-deadline-20261003.json.

* Fresh lifecycle boundary audit
The maintained native-runtime-lifecycle-run entrypoint runs the new
examples/runtime_lifecycle.rs supervisor. The supervisor never initializes
Gerbil; each case runs in a fresh supervised process. It only queries SIGTERM
disposition and stdin open-file flags, and never replaces handlers or restores
flags. Native program identity is still ed7540bf. Raw eight-case receipts are
native-runtime-lifecycle-20261003.json. Both supervisors correctly exit one.

| case | runtime-rust | runtime-scheme |
|------+--------------+----------------|
| Baseline ordinary return | exit 0 | exit 0 |
| Baseline SIGTERM | signal 15 | signal 15 |
| Native ordinary return | exit 0; stdin gate red | exit 0; stdin gate red |
| Native idle SIGTERM | no exit in 2s; supervised SIGKILL | no exit in 2s; supervised SIGKILL |

For both native cases, stdin flags changed from 0 to 4 (O_NONBLOCK on this
macOS host) and the SIGTERM handler changed from default to installed.
The stdio field in this probe covers stdin only, not stdout/stderr. Its protocol
tolerates WouldBlock to reach the signal check, but flag mutation remains a
separate red gate. The initial blocking-stdin probe panicked on WouldBlock;
those early/stale-binary attempts are excluded from signal qualification.
All supervised processes were reaped. No unrelated processes were stopped.

The same symptom in both lanes rules out describing this as only one queue's
bug. The installed dcd677c source installs SIGTERM/child handlers and the
current native service waits in a blocking C condition variable when idle.
This is not a complete native green-thread I/O integration. The fresh idle
probe did NOT reproduce signal 11; it does not establish the cause of the prior
active-corpus termination crash, and no TLS-crash cause is inferred.

The current unrestricted lazy first-parse initialization has no demonstrated
host-resource ownership policy. A bridge-side restore AFTER setup would not
qualify the race window during setup. Closing this under the no-kernel-change
constraint requires an explicit host contract decision, not test serialization,
an implicit process parser fallback, busy polling, or ignored failures.

* Extended Tokio stream qualification
Tokio's io-util feature is enabled only for development tests. The new focused
case joins producers and consumers on 32 in-memory duplex streams, each with
8 bytes of capacity (less than one document), then admits native parsing with
8 semaphore permits. All stream reads/writes and native completions finish
under a 20-second test deadline; permits return. Socket, file and process APIs
are not claimed by this in-memory stream test.

The updated eleven-case public suite passed on the same ed7540bf native program:
- Rust: gerbil_rowan_cutover-2a6b8bd75f933118, 11 passed, 1.42 seconds.
- Scheme: gerbil_rowan_cutover-b2b28273eb9b4265, 11 passed, 2.07 seconds.

Both were release-profile binaries using the explicit local Apple linker
diagnostic. Root dev opt-level 2/build override 2 and release opt-level 3/Thin LTO
remain unchanged. The scale receipts above are the previous completed round,
not a new 44000-parse rerun after this test-only feature addition.

Decision needed before a lifecycle implementation changes the public contract:
authorize an explicit startup-only native initialization boundary before the
host starts Tokio workers, Python worker threads or subprocesses, with a
declared host stdio/signal ownership policy and checked runtime admission; or
retain unrestricted lazy initialization and require an upstream supported
embedding ownership seam. Startup-only admission is a proposed contract, not
an implemented fix or proof that the prior signal-11 fault is solved. A later
patch must qualify native wakeup, cleanup, host-child and Python boundaries
separately without kernel changes or a parser process fallback.

Two new tests cover single-thread Tokio scheduler progress with 128 semaphore-
bounded tasks and keeping the permit until running blocking/native work exits
after its waiter is canceled. Fresh release test binaries linked against the
214-module ed7540bf program passed all ten public cases in both features:
runtime-rust in 0.39 seconds and runtime-scheme in 0.72 seconds. These supersede
the earlier checks on the prior 81e321d9 program for this focused test suite.
They are not a receipt for all Org semantics or the complete Tokio ecosystem.
The fresh focused binaries are gerbil_rowan_cutover-849e566dc4db7204 (Rust)
and gerbil_rowan_cutover-8fbeea1c629b41d7 (Scheme), under target/release/deps.

Tokio remains a development dependency for integration and benchmarks. The
production runtime-rust native owner still uses its bounded synchronous queue;
this receipt must not be described as replacing that owner with a Tokio runtime.
The covered ecosystem surface is task scheduling, bounded admission, cancellation
and timer progress. Network/file I/O and tokio::process coexistence are not covered.
